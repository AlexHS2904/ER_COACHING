# Local deterministic Checkout failure recovery

The recovery migration has been applied to ER_COACHING and its structure verified.
Do not reapply it. Subsequent worker/reconciliation changes remain local and are
described in [expiration reconciliation](stripe-expiration-reconciliation.md).

Migration generated by Supabase CLI:
`20261028201527_stripe_failed_attempt_recovery.sql`.

## Contracts

- `create_stripe_booking_hold_v1`: unchanged, including its signature and fixed
  deadline. Recovery never calls it or `create_booking`.
- `claim_stripe_checkout_v1`: same signature/JSON contract. Reuses any active
  creating/open/unknown attempt. With no active attempt, permits a successor
  only after a proven rejected failure with no Session, PaymentIntent or received
  payment. The failed row remains untouched.
- `save_stripe_checkout_v1`: same signature/result; additionally records successful
  creation provenance when a Session is bound. Expired holds still bind returned
  Sessions for reconciliation and return false as before.
- Existing partial unique active-attempt index: unchanged.
- New service-only RPCs, SECURITY DEFINER and `search_path=pg_catalog,pg_temp`:
  `begin_stripe_checkout_creation_v1(uuid,uuid,uuid)` and
  `record_stripe_checkout_failure_v1(uuid,uuid,uuid,text,text)`.

The additive `checkout_creation_state` column defaults to `ambiguous`. Existing
attempts are never inferred to be safe failures; their original fields remain
unchanged. New attempts explicitly start with `not_started`.

## Dispatch and errors

Before sending Stripe create, the begin RPC locks booking then attempt, checks
eligibility/deadline/lease, and commits a dispatch marker. Only its first dispatch
returns true (`in_flight`). A second dispatch, a previous unknown, or legacy
provenance yields ambiguity. A crash or lost database response cannot reset it.

The client retains `maxNetworkRetries: 1`. The documented SDK `request` event is
counted for the exact Checkout POST/key. More than one physical send means that
an earlier send could have succeeded, even if the final response is a definitive
400/401/403. Missing telemetry also fails closed. The installed SDK retries some
closed-socket errors even with retries disabled, so changing the retry setting
alone would not establish certainty.

Only a recognized deterministic SDK error from direct create, a first durable
dispatch, and exactly one physical send can request `failed`. The failure RPC
checks current ownership, lease, dispatch state and absence of Session/payment.
Otherwise the outcome stays unknown or the stale writer is ignored. Stored error
codes are fixed, never raw Stripe messages, credentials or customer details.

A returned Session crosses the creation boundary. Save errors are handled in a
separate catch: unknown when not yet bound; an already committed open Session
retains its identity. Retrieval errors preserve the known Session and never fail
its creation. Database write errors propagate; dispatch markers remain available
for conservative recovery.

## Successor and concurrency

`failed/rejected` is immutable evidence. A successor has a new UUID and the same
`booking-checkout/<attempt UUID>` idempotency-key format. Its amount, currency,
URLs, expiration and payload come from the original trusted attempt; only
`metadata.payment_attempt_id` changes. New initial payloads omit the deprecated
`payment_method_types`; the service also strips it from legacy persisted payloads.
No automatic background retry creates successors for configuration errors.

Booking row locks plus the unchanged partial unique index serialize concurrent
claims. Only one successor owns the creation lease. Unknown attempts always keep
their original ID/key/payload. No booking or deadline is created/updated by recovery.
Paid, cancelled, expired and review-required bookings cannot start a successor.

## Verification and remaining scope

Tests use isolated PostgreSQL, the actual service and SDK with fake HTTP transport.
They cover legacy data, repeated application, SQL/service races, successor identity,
financial/payload/deadline preservation, timeouts, SDK internal retries, stale leases,
lost database writes/responses, expiry and recovered payment through finalization.
Calendar/email APIs are doubles; no real records or payments are touched.

Reconciliation now uses persisted backoff and finite technical review, without
reclassifying an unknown as a deterministic failure or repairing historical rows.
